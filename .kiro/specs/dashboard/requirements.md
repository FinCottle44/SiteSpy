# Requirements Document

## Introduction

SiteSpy is a multi-tenant construction progress monitoring platform. The ingest pipeline is live — pole-mounted Axis cameras POST hourly JPEG snapshots to S3 via a Lambda, with `IMG#` records in DynamoDB. This spec covers the Phase 0 MVP web dashboard: a React application where authenticated users log in, view their assigned sites and cameras, browse snapshot galleries, monitor camera health via heartbeat indicators, and raise flags on cameras exhibiting issues.

The dashboard is built with React 18 + TypeScript, styled with Tailwind CSS and shadcn/ui (restyled to SiteSpy tokens), authenticated via AWS Amplify against Cognito, and hosted on AWS Amplify Hosting in `eu-west-2`.

## Glossary

- **Dashboard**: The SiteSpy React web application that authenticated users interact with to view snapshots and manage camera flags.
- **Site**: A physical construction location containing one or more cameras, belonging to a single tenant.
- **Camera**: An Axis P1455-LE device at a site that pushes hourly JPEG snapshots to S3.
- **Snapshot**: A single JPEG image captured by a camera at a specific timestamp.
- **Tenant**: A construction company using the SiteSpy platform; the data isolation boundary.
- **Super_Admin**: A platform operator who can access all tenants and all sites.
- **Tenant_Admin**: A company administrator who can access all sites within their tenant.
- **User**: A regular user assigned to specific sites via `custom:site_access`.
- **Heartbeat**: A status indicator derived from the age of the most recent snapshot for a camera.
- **Flag**: A report raised against a specific camera indicating a health or quality issue.
- **Pre-signed_URL**: A time-limited S3 URL generated by the API Lambda to grant temporary image access without exposing S3 directly.
- **Gallery**: A paginated, chronological grid of snapshot thumbnails for a single camera.
- **Lightbox**: A full-resolution image viewer with metadata and keyboard/swipe navigation.
- **Flag_Review_Console**: An admin-only view listing open and acknowledged flags for triage.
- **Amplify**: AWS Amplify library used for Cognito authentication flows in the frontend.
- **ID_Token**: The Cognito JWT containing user claims (`cognito:groups`, `custom:tenant_id`, `custom:site_access`) sent as a Bearer token on API calls.

## Requirements

### Requirement 1: User Authentication

**User Story:** As a user, I want to log in securely using my Cognito credentials, so that I can access the dashboard and view my assigned sites.

#### Acceptance Criteria

1. THE Dashboard SHALL use Amplify to handle login and signup flows against the Cognito User Pool.
2. WHEN an unauthenticated user attempts to access any dashboard route, THE Dashboard SHALL redirect the user to the login page.
3. WHEN a user successfully logs in, THE Dashboard SHALL extract `cognito:groups`, `custom:tenant_id`, and `custom:site_access` from the ID_Token and derive the effective role (Super_Admin, Tenant_Admin, or User).
4. THE Dashboard SHALL pass the ID_Token as `Authorization: Bearer <token>` on every API call.
5. THE Dashboard SHALL use Amplify's built-in secure token management and not store raw JWTs in localStorage.
6. WHEN any API call returns a 403 status, THE Dashboard SHALL display a full-page "Access Denied: You do not have access to this site." message with a link back to the site list.

### Requirement 2: Role-Based Navigation

**User Story:** As a user, I want to see navigation appropriate to my role, so that I can access the features I am authorized to use.

#### Acceptance Criteria

1. WHEN the effective role is Super_Admin, THE Dashboard SHALL render a tenant picker, a global flag review console link, and all sites across the selected tenant.
2. WHEN the effective role is Tenant_Admin, THE Dashboard SHALL render all sites within the tenant, a flag review console link scoped to the tenant, and hide the tenant picker.
3. WHEN the effective role is User, THE Dashboard SHALL render only the sites listed in `custom:site_access`.
4. WHILE a User has only one site in `custom:site_access`, THE Dashboard SHALL hide the site picker and navigate directly to that site.

### Requirement 3: Site View with Multi-Camera Hero

**User Story:** As a user, I want to see the latest snapshot from every camera at my site in a single view, so that I can quickly assess current conditions.

#### Acceptance Criteria

1. WHEN a user opens a site, THE Dashboard SHALL call `GET /sites/{site_id}` to fetch the camera list and `GET /snapshots/latest?site_id={site_id}` to fetch the latest image for every camera.
2. WHILE the site has a single camera, THE Dashboard SHALL display the sole image at full width.
3. WHILE the site has multiple cameras, THE Dashboard SHALL display a responsive tile grid with one tile per camera, each labelled with the camera name.
4. THE Dashboard SHALL display a heartbeat indicator on each camera tile derived from that camera's `age_seconds` value.
5. WHEN `age_seconds` exceeds 7200 for a camera, THE Dashboard SHALL display "Camera may be offline" on that camera's tile.
6. WHEN a user clicks a camera tile on a multi-camera site, THE Dashboard SHALL navigate to a single-camera focused view for that camera.

### Requirement 4: Timeline and Gallery

**User Story:** As a user, I want to browse the historical archive of snapshots for a specific camera, so that I can review construction progress over time.

#### Acceptance Criteria

1. THE Gallery SHALL always be scoped to a single camera.
2. WHILE the site has multiple cameras, THE Dashboard SHALL display a camera selector at the top of the gallery view.
3. WHILE the site has a single camera, THE Dashboard SHALL hide the camera selector.
4. WHEN the gallery loads, THE Dashboard SHALL call `GET /snapshots?site_id={site_id}&camera_id={camera_id}&from={date}&to={date}` to fetch a paginated list of snapshots.
5. THE Dashboard SHALL display snapshots as a responsive grid of thumbnails in chronological order, newest first.
6. THE Dashboard SHALL provide a date picker to filter snapshots by day.
7. WHEN the API response contains a `next_cursor` field, THE Dashboard SHALL support pagination to load additional snapshots.
8. WHEN there are gaps (missing hours) in the snapshot timeline, THE Dashboard SHALL show a placeholder or skip the gap without displaying broken images.
9. WHEN no snapshots exist in the selected date range, THE Dashboard SHALL display a neutral empty state with the date picker highlighted.

### Requirement 5: Lightbox Viewer

**User Story:** As a user, I want to view a snapshot at full resolution with metadata, so that I can inspect construction details closely.

#### Acceptance Criteria

1. WHEN a user clicks a thumbnail in the gallery, THE Dashboard SHALL open a full-resolution lightbox view of that snapshot.
2. THE Lightbox SHALL display the snapshot's timestamp formatted to the site's timezone, the site name, and the camera name.
3. WHEN the user presses arrow keys or swipes, THE Lightbox SHALL navigate between images of the same camera in chronological order.
4. THE Lightbox SHALL provide a close action that returns the user to the gallery.

### Requirement 6: Heartbeat Status Monitor

**User Story:** As a user, I want a persistent status indicator showing camera health for the current site, so that I can notice connectivity issues at a glance.

#### Acceptance Criteria

1. THE Dashboard SHALL display a persistent heartbeat indicator in the header summarizing the worst camera status for the currently viewed site.
2. WHILE all cameras at the site have `age_seconds` less than 5400 (90 minutes), THE Dashboard SHALL display the heartbeat indicator as green.
3. WHILE any camera at the site has `age_seconds` between 5400 and 10800 (90–180 minutes), THE Dashboard SHALL display the heartbeat indicator as yellow.
4. WHILE any camera at the site has `age_seconds` greater than 10800 (180 minutes), THE Dashboard SHALL display the heartbeat indicator as red.
5. WHEN the user hovers over the heartbeat indicator, THE Dashboard SHALL reveal a per-camera breakdown showing each camera's status.
6. THE Dashboard SHALL convey heartbeat status using both color and an icon or text label, not color alone.

### Requirement 7: Flag a Camera

**User Story:** As a user, I want to raise a flag on a camera that appears to have an issue, so that an admin is notified and can investigate.

#### Acceptance Criteria

1. THE Dashboard SHALL display a "Flag this camera" button on every camera tile in the hero view, on the single-camera focused view, and in the lightbox overlay.
2. WHEN the user activates the flag button, THE Dashboard SHALL display a form with a required Reason dropdown (Stale image, Physical damage, Obstruction, Image quality, Other) and an optional Note textarea (max 1000 characters).
3. WHEN the selected Reason is "Other", THE Dashboard SHALL require the Note field to be filled.
4. THE Flag form SHALL pre-fill the camera name so the user knows which camera is being flagged.
5. WHEN the user submits the flag form, THE Dashboard SHALL call `POST /flags` with `site_id` and `camera_id` and display a confirmation toast: "Flag raised. An admin has been notified."
6. WHEN the API returns an existing open flag (duplicate suppression), THE Dashboard SHALL display a toast: "This issue has already been flagged and is being reviewed."
7. WHILE an open or acknowledged flag exists for a camera, THE Dashboard SHALL display a warning badge on that camera's tile and focused view showing the flag reason (e.g., "⚠ Flagged: Physical damage").
8. WHEN the user clicks the flag badge, THE Dashboard SHALL show the current flag details and status.

### Requirement 8: Flag Review Console

**User Story:** As a Tenant_Admin or Super_Admin, I want to review and triage flagged cameras, so that I can coordinate maintenance and resolve issues.

#### Acceptance Criteria

1. THE Dashboard SHALL provide a flag review console at the `/flags` route accessible only to Tenant_Admin and Super_Admin roles.
2. WHILE the user is a Tenant_Admin, THE Flag_Review_Console SHALL display flags within their tenant only.
3. WHILE the user is a Super_Admin, THE Flag_Review_Console SHALL display flags across all tenants with a tenant filter dropdown.
4. THE Flag_Review_Console SHALL display each flag row with: site name, camera name, reason, note, source (user-raised or auto-raised), raised-by name, raised-at timestamp (relative), status badge, and a thumbnail of the flagged camera's latest snapshot.
5. WHEN the user is a Super_Admin, THE Flag_Review_Console SHALL additionally display the tenant name on each flag row.
6. THE Flag_Review_Console SHALL provide Acknowledge, Resolve, and Dismiss action buttons on each flag row.
7. WHEN the user activates an action button, THE Dashboard SHALL open a modal for optional admin notes before calling `PATCH /flags/{flag_id}`.
8. THE Flag_Review_Console SHALL provide filters for: status (default: open + acknowledged), reason, site, camera, and source.
9. THE Flag_Review_Console SHALL support sorting by newest first (default), oldest first, and by reason.
10. WHEN the user clicks a flag row's deep link, THE Dashboard SHALL navigate to the site's gallery with the camera selector pre-set to the flagged camera.

### Requirement 9: Image Access via Pre-signed URLs

**User Story:** As a user, I want to view snapshot images securely, so that tenant data isolation is maintained.

#### Acceptance Criteria

1. THE Dashboard SHALL retrieve all images exclusively via Pre-signed_URLs returned by the API.
2. THE Dashboard SHALL NOT have direct S3 access or embed raw S3 URLs.
3. WHEN a Pre-signed_URL expires or returns an error, THE Dashboard SHALL display a placeholder and offer a retry action.

### Requirement 10: Timezone Rendering

**User Story:** As a user, I want timestamps displayed in the site's local timezone, so that I can correlate snapshots with on-site events.

#### Acceptance Criteria

1. THE Dashboard SHALL render every displayed timestamp in the viewed site's timezone (from the site's `timezone` field), not in the browser's local timezone.
2. THE Dashboard SHALL use a shared Timestamp component for all timestamp rendering, with no raw `.toLocaleString()` calls.

### Requirement 11: Error and Empty States

**User Story:** As a user, I want clear feedback when something goes wrong or no data exists, so that I am never left with a blank screen or confusion.

#### Acceptance Criteria

1. WHEN a network error occurs, THE Dashboard SHALL display a toast notification with a Retry button and not render a white screen.
2. WHEN a 403 response is received, THE Dashboard SHALL display a full-page access denied state with tenant and role context and a link back to the site list.
3. WHILE a site has no cameras registered, THE Dashboard SHALL display a helpful card with a "Register a camera" call-to-action for admins, or "Ask your admin to register a camera" for users.
4. WHILE a camera's latest snapshot has `age_seconds` exceeding 7200, THE Dashboard SHALL display an in-view banner with the last-received timestamp and a "Raise flag" button.

### Requirement 12: Accessibility

**User Story:** As a user with accessibility needs, I want the dashboard to be fully navigable and understandable, so that I can use all features regardless of ability.

#### Acceptance Criteria

1. THE Dashboard SHALL conform to WCAG 2.2 Level AA.
2. THE Dashboard SHALL provide a visible focus ring on every interactive element.
3. THE Dashboard SHALL ensure all interactive targets have a minimum size of 40×40 pixels.
4. THE Dashboard SHALL provide a meaningful accessible label on every interactive element.
5. THE Dashboard SHALL convey status information using icons and text labels in addition to color.
6. THE Dashboard SHALL support full keyboard navigation for all views and actions.
